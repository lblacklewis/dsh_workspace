## 🔧 重建步骤（服务器全清后）

### 1. 恢复 MySQL 配置

```bash
cat > /etc/mysql/conf.d/crmeb.cnf << 'EOF'
[mysqld]
character-set-server=utf8mb4
collation-server=utf8mb4_unicode_ci
innodb_buffer_pool_size=128M
innodb_log_buffer_size=8M
max_connections=50
performance_schema=OFF
skip-log-bin
default-authentication-plugin=mysql_native_password
EOF
systemctl start mysql redis-server
```

> ⚠️ `default-authentication-plugin=mysql_native_password` 必须保留，否则老版本
> MySQL Connector/J 无法连接。

**Redis 密码必须写进配置文件**（只 `CONFIG SET` 设的话，一重启就丢）：

```bash
grep -q "^requirepass" /etc/redis/redis.conf \
  && sed -i 's/^requirepass .*/requirepass redis_dMtNMj/' /etc/redis/redis.conf \
  || echo "requirepass redis_dMtNMj" >> /etc/redis/redis.conf
systemctl restart redis-server

# 验证：不带密码应被拒，带密码应 PONG
redis-cli PING                                    # NOAUTH Authentication required.
redis-cli -a redis_dMtNMj --no-auth-warning PING  # PONG
```

> 🔴 **踩坑记录（2026-10-27 后台登录不了的真凶）**
> Redis 无密码、而后端 `application-dev.yml` 配了 `password: redis_dMtNMj` 时，
> Jedis 抛 `ERR AUTH <password> called without any password configured`，
> 连接池拿不到连接 → **token 无法读写 → 所有鉴权接口返回 401**。
>
> 迷惑点：HTTP 状态码是 **200**，只有 body 是 `{"code":401,...}`。
> 排查技巧：看 nginx access log 的响应体大小，**49 字节** 就是这个 401 响应
> （`{"code":401,"message":"未登录，请登录！"}` 恰好 49 字节）。
> 患者症状：登录按钮点完变灰、页面反复弹「无效的会话」「Verification failed」。

## ⚡ 性能优化（2026-10-27，解决 H5「图多、卡、慢」）

首屏体积 **2.7MB → 0.67MB（省 75%）**。

### 1. nginx gzip（最大收益）

默认 `gzip_types` 是**注释掉的**，所以 JS/CSS 完全没压缩：

```bash
# /etc/nginx/conf.d/performance.conf
gzip_vary on; gzip_proxied any; gzip_comp_level 5; gzip_min_length 1024;
gzip_types text/plain text/css text/xml text/javascript
           application/json application/javascript application/x-javascript
           application/xml application/xml+rss image/svg+xml
           font/woff font/woff2 application/font-woff;
open_file_cache max=10000 inactive=60s;
open_file_cache_valid 120s;
open_file_cache_min_uses 2;
open_file_cache_errors on;
```

> ⚠️ 不要重复写 `gzip on;` —— nginx.conf 里已有，会报 `"gzip" directive is duplicate` 导致重载失败。

效果：`chunk-vendors.js` 683KB→**214KB**，`index.js` 494KB→**139KB**（省 70%）。

### 2. 图片批量压缩

CRMEB 演示图多为 1500×690 的大 PNG，单张 500KB–2.7MB。

```bash
apt-get install -y imagemagick pngquant
# 先备份
tar -czf /root/crmebimage-backup.tar.gz -C /opt/storapp/crmeb crmebimage
# 批量：等比缩到最大 800px 宽 + pngquant 有损压缩（文件名不变）
bash /root/optimize-images.sh     # 见 docs/optimize-images.sh
```

结果：**74MB → 23MB（省 71%）**，120 张图，单张最大 2.7MB→159KB。
文件名与格式均不变，DB 引用无需改动。

### 3. 浏览器缓存

H5 的带 hash 资源设 `immutable` 一年，图片 30 天，`index.html` 不缓存。
图片目录加 `access_log off` 减少日志写盘。

## 🛒 前端接口联调速查（2026-10-27 实测跑通下单）

**请求头**：`Authori-zation: <裸 token>`

> ⚠️ **不要加 `Bearer ` 前缀**。`FrontTokenComponent.getToken()` 会把常量
> `USER_TOKEN_REDIS_KEY_PREFIX = "TOKEN_USER:"` 当前缀剥掉，而 Redis 里的 key
> 就是 `TOKEN_USER:<token>`。加了 `Bearer ` 会拼成 `TOKEN_USER:Bearer xxx` → 查不到 → **402**。

**完整链路（已验证 `¥18.80 × 4 = ¥75.20`）**：

```
POST /front-api/api/front/login                    {account, password, spread_spid}
GET  /front-api/api/front/product/detail/{id}
POST /front-api/api/front/cart/save                {productId, cartNum, productAttrUnique}
GET  /front-api/api/front/cart/list?isValid=true&page=1&limit=10
POST /front-api/api/front/order/pre/order           → preOrderNo
POST /front-api/api/front/order/create              → orderNo
```

### 踩坑

| 现象 | 真实原因 |
|------|----------|
| `cart/list` 报 `Required Boolean parameter 'isValid' is not present` | 该接口 `isValid` 是**必填** `@RequestParam` |
| 加购报 `商品属性id不能为空` / `未找到对应的商品SKU` | **`productAttrUnique` 要传 SKU 行的 `id`**，不是 `unique` 字段。代码里是 `eq(StoreProductAttrValue::getId, attrId)` |
| 预下单报 `Index: 0, Size: 0` | 两种原因：① 用户**没有收货地址**；② `preOrderType` 传错 |
| 下单报 `预下单订单详情列表不能为空` | `preOrderType` 是**字符串枚举 `"shoppingCart"` / `"buyNow"`**，不是 `"0"`/`"1"` |

`preOrderType` 只认这两个字面量（`OrderServiceImpl:1491,1496`），传别的值时两个
`if` 都不进，`detailVoList` 保持空 → 后续 `.get(0)` 抛 `IndexOutOfBoundsException`。

### 需要用 PowerShell 调 curl 时的坑

- `curl.exe -d` 的 JSON 要用 `'{\"k\":\"v\"}'`（PS 5.1 转义），**嵌套数组/对象会被弄坏**，
  稳妥做法：把 body 写文件再 `--data-binary "@file"`。
- 修数据前先跑一次 `SHOW COLUMNS`：`unique` / `value` / `status` 是 MySQL 保留字，
  列名对不上时加 `2>/dev/null` 会把 SQL 报错一起吞掉，看起来像"查不到数据"。

## 🚨 首页装修会被「恢复默认」覆盖（2026-10-27 实际发生过）

**现象**：首页突然变回 CRMEB 演示模板 —— FUN PARADISE 动物园 banner、
彩色「限时秒杀/拼团活动/浏览记录/砍价中心/抽奖活动」金刚区、精选榜单拼图，
底部菜单也跟着变回演示样式。

**原因**：`eb_theme.home_data` 被 `home_default_data` 整列覆盖
（两者内容变成完全一致）。触发点在**后台装修页**：只要在里面点了保存/恢复默认，
就会把当前页面的数据整份写回 `home_data`。已经清过 Redis 也没用——**缓存是结果不是原因**。

**恢复**：

```powershell
cd D:\project\StorApp\crmeb_java\docs
.\restore-theme.ps1            # 先本地校验备份
.\restore-theme.ps1 -Apply     # 上传并写回，自动清 Redis
```

备份文件：`docs/首页装修_最终版.sql`（base64，105165 字符）、
`docs/screenshots/theme-final.json`（明文 JSON，方便 diff）。

**排查用的一条 SQL**——两者相同就说明被覆盖了：

```sql
SELECT home_data = home_default_data AS 被覆盖 FROM eb_theme WHERE id = 1;
```

**预防**：后台「页面装修」不要点保存/恢复默认；
改装修走 `docs/rebuild-theme-*.ps1` 脚本，改完立刻跑一次备份校验。

## 🔧 底部导航整条不显示的三个原因（2026-10-28 排查）

CRMEB 在 `pages/index/index.vue:248` 调 **`uni.hideTabBar()`**，把 uni-app 原生 tabBar 隐藏了
（`uni-tabbar` 上会留下内联 `display:none`），底部导航改由自研组件
`components/pageFooter/index.vue` 渲染（DOM 是 `.page-footer-fixed > .page-footer-wrapper > .page-footer`）。

**`static/index.css`（96KB，uni-app 的 H5 基础样式）没有被 `index.html` 引用**——
`index.html` 里 `<link>` 数量是 **0**，所有业务样式都是 webpack 在 JS 里内联注入的。
后果是 `uni-view` / `uni-image` 全部退化成浏览器默认值，组件里依赖基础样式的布局就塌了：

| # | 塌陷点 | 现象 |
|---|--------|------|
| a | `uni-view` 退化成 `display:inline` | `.page-footer-wrapper` 宽度 **0** |
| b | `.page-footer` 是 `position:absolute`，父层没高度 | 整条高度 **0** |
| c | `uni-image > div` 高度 0 | 图标不显示，只剩文字 |
| d | scoped 里写 `.foot-item image`，实际 DOM 是 `uni-image` | 尺寸/间距失效，图标压住文字 |

**不要**在 `index.html` 里补 `<link href="/static/index.css">`——那份 CSS 与现有构建不自洽，
加载后整页会**变全白**。

正确做法是按需补最小样式（现放在 `docs/h5-override.css`，构建后用
`docs/apply-h5-override.ps1` 注入）。底部导航那几段用**绝对定位**写死，
不依赖 flex（缺基础样式时 flex 行为不可靠）。

### 另一个坑：主题色存在 `theme_data` 而不是 `home_data`

`--view-theme` 由 `app/utils/theme.js` 的 `setThemeColor()` 设置，
数据来自 `GET /front-api/api/front/theme_info/theme`，读的是 **`eb_theme.theme_data`**：

```json
{"theme_color":"#E93323","gradient_color":"#FF7931","sub_color":"#FE960F","light_color":"rgba(233, 51, 35, 0.1)"}
```

只改 `home_data` 的话，首页组件是 teal、但**选中态/价格/按钮仍是 CRMEB 红**。两处都要改：

```sql
UPDATE eb_theme SET theme_data = REPLACE(REPLACE(REPLACE(REPLACE(theme_data,
  '#E93323','#0D9488'), '#FF7931','#14B8A6'), '#FE960F','#0D9488'),
  '233, 51, 35','13, 148, 136') WHERE id = 1;
```

> ⚠️ `light_color` 是 `rgba(233, 51, 35, 0.1)` —— **逗号后带空格**，
> 替换时要匹配 `233, 51, 35`，写成 `233,51,35` 是匹配不上的。

### 底部导航图标顺序（容易搞反）

`getMenuImage(item, active)` 是 **`active ? imgList[0] : imgList[1]`** ——
**`imgList[0]` 是选中态**，`imgList[1]` 是常态。反了会导致选中项显示灰色图标。

### PowerShell 拼数组的坑

```powershell
# 错：逗号优先级高于 +，结果是「两个 URL 用空格拼成一个字符串」
$m.imgList = @($IMG + "a.svg", $IMG + "b.svg")   # -> ['url1 url2']

# 对：先各算各的再用 ArrayList
$on  = $IMG + "a.svg"
$off = $IMG + "b.svg"
$arr = New-Object System.Collections.ArrayList
[void]$arr.Add($on); [void]$arr.Add($off)
$m.imgList = $arr.ToArray()
```

### 截图排查的坑

H5 的布局视口是**设备宽度的约 2 倍**（页面按 750rpx 渲染，浏览器缩放显示）：
`setViewport(390x844)` 时 `window.innerWidth` 其实是 **756**。
用普通截图只能截到左上角约一半，**底部永远是空的**，会误判成「底部没渲染」。

正确排查方式：
```js
await page.setViewport({ width: 390, height: 844, deviceScaleFactor: 2, isMobile: true, hasTouch: true });
await page.waitForSelector('.page-footer-fixed', { timeout: 60000 });  // 别用 networkidle2，会假完成
await page.screenshot({ path: 'x.png', fullPage: true });              // 必须 fullPage
// 或者直接截元素：const el = await page.$('.page-footer-fixed'); await el.screenshot(...)
```

## 🚨 最容易误判的坑：改完文件「不生效」/「页面白屏」

**根因：`open_file_cache`。**

为了提速，`/etc/nginx/conf.d/performance.conf` 里加了文件句柄缓存。它按 **inode** 缓存句柄：

| 场景 | 后果 |
|------|------|
| **原子替换**（写 tmp + `mv`/`os.replace`，inode 变了） | 缓存句柄还指向**旧 inode** → nginx 继续发**旧内容**，看着像"改了没生效" |
| **原地覆盖写**（`open(w)` 先截断再写） | nginx 读到**写了一半的文件** → 浏览器收到截断 HTML → **白屏** |

日志特征（原地覆盖写时）：

```
[alert] pread() read only 2291 of 3323 from "/var/www/storapp/h5/index.html"
        while sending response to client
```

**踩坑经过**：连续改 `index.html` 时页面反复"白屏"，我一度误判成
「`static/index.css` 与构建不自洽」并写进了文档。实际用请求拦截做 A/B 对比后：
加载 index.css 后页面高度**完全一样（2319）**，而高度为 0 的图片从 **5 个降到 1 个**
—— 它是**该加载的**，之前的白屏是截断造成的假象。

**正确做法（两条都要）**：

1. `/etc/nginx/conf.d/performance.conf` 把缓存压到 5 秒兜底：
   ```nginx
   open_file_cache max=10000 inactive=5s;
   open_file_cache_valid 5s;
   ```
2. 部署脚本写完文件 **必须 `systemctl reload nginx`**，
   然后对比「磁盘文件大小」和「nginx 返回大小」是否一致 —— 不一致就是缓存没刷。

**排查口诀**：磁盘上是新的、浏览器是旧的 → 先 `systemctl reload nginx` 再看，
别急着怀疑代码。
