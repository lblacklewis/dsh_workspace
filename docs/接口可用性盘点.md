### 1.3 关于"500"的口径说明（重要）

CRMEB 的 `GlobalExceptionHandler` 把**所有异常都包成 HTTP 200 + 业务 code 500**。所以：
- **HTTP 状态码没有区分度**，必须看业务 `code`。
- 业务 `code=500` 里**绝大多数是正常的参数校验提示**（如"Required String parameter 'type' is not present"、"xx不能为空"），**不代表接口坏了**。
- 真正的故障是下面这些**特征报文**：`Access is denied`、`一号通平台接口接口请求失败`、`微信接口调用失败`、`易联云 未开启打印`、`IndexOutOfBoundsException`。

## 三、不可用接口清单

### 3.1 【根因 A + B】权限体系缺陷 → 44 个后台接口对所有人永久 403

**现象**：用**超管账号 admin**（权限列表实测为 `["*:*:*"]`）调用，返回 `{"code":500,"message":"Access is denied","data":null}`。
（同一异常在异常日志里还会以中文 `org.springframework.security.access.AccessDeniedException: 不允许访问` 出现，两种文案来自同一次拒绝。）

**根因定位**（三步取证）：

1. 统计代码里所有 `@PreAuthorize("hasAuthority('...')")` 要求的权限点 → **379 个**。
2. 统计 `eb_system_menu` 中已定义的 `perms` → **312 个**。
3. 集合差集 → **74 个权限点在数据库里不存在**；其中 **70 个**能对应到具体接口（4 个是代码里已无对应端点的冗余权限串）。

**关键证据**：

```sql
-- 这些权限点在菜单表里一行都没有
SELECT COUNT(*) FROM eb_system_menu WHERE perms='admin:statistics:user:overview';  -- 0
SELECT COUNT(*) FROM eb_system_menu WHERE perms='admin:system:store:list';         -- 0
SELECT COUNT(*) FROM eb_system_menu WHERE perms='admin:system:user:level:list';    -- 0
```

```sql
-- 分组统计
SELECT COUNT(*) FROM eb_system_menu
 WHERE perms LIKE 'admin:statistics:user%' 
    OR perms LIKE 'admin:statistics:trade%' 
    OR perms LIKE 'admin:statistics:product%';   -- 0
```

**为什么"配一下就可用"这个选项不存在**：
`UserDetailServiceImpl` 的鉴权路径是

```java
if (roles.contains(1)) {                       // 超管
    menuList = systemMenuService.getAllPermissions();   // 从 eb_system_menu 取所有 perms
} else {
    menuList = systemMenuService.findPermissionByUserId(user.getId());
}
```

权限字符串**只能来自 `eb_system_menu.perms` 这一列**。该列为空 → 无论给哪个角色授权、无论是不是超管，都拿不到这个权限字符串。
并且代码中**没有任何 `PermissionEvaluator` 或通配符匹配实现**（已全仓库检索，结果为空），所以 `*:*:*` 只是被当作一个**普通字符串**塞进权限列表，对 `hasAuthority('admin:statistics:user:overview')` 这种**精确匹配**不起任何作用。

**结论**：这 44 个接口的 403 **不是"没配权限"**——其中 32 个是"权限点根本不存在，无法被授予"（**代码/数据缺陷**），12 个是"权限点存在但随菜单被软删"（**配置问题**）。

## 四、接口调用要点（接小程序/支付的同事请直接抄）

这一节是踩坑总结，与任务描述给的说明**有出入，实测为准**。

### 4.1 认证方式（实测）

| 项 | 实测结论 |
|----|---------|
| 后台请求头 | `Authori-zation: <token>` —— **必须是裸 token，加 `Bearer ` 直接 401** |
| 后台登录 body | `{"account":"admin","pwd":"123456"}` —— 字段名是 **`pwd` 不是 `password`**，且**传明文**（服务端自己 DES 加密后比对） |
| 后台 login 响应 | `data.token` 为 32 位无横线 UUID |
| 前台请求头 | `Authori-zation: <token>` —— 同样**裸 token** |
| 前台登录 body | `{"account":"13800138000","password":"123456","spread_spid":"0"}` —— **字段名是 `account` 不是 `phone`**（源码 `LoginRequest.phone` 上标了 `@JsonProperty("account")`）；推广人 id 是 `spread_spid` |
| 前台 token 过期 | 返回 **402**（`{"code":402,"message":"token过期，请登录！"}`），非 401 |
| 后台 token 无效 | 返回 **401**（`{"code":401,"message":"未登录，请登录！"}`） |
| 一台机器只能一个有效 token？ | **不是**。多 token 并存，但 `GET /api/front/logout` 会让**该账号所有旧 token 失效** |

### 4.2 状态码口径

`GlobalExceptionHandler` 把业务异常统一包成 **HTTP 200 + body 里的 `code`**。
唯一会真正返回 HTTP 非 200 的是 **Spring 层面的 404（NoHandlerFound）**。
**因此对接时必须判断 body 的 `code`，不能只看 HTTP 状态。**

### 4.3 权限模型

权限字符串**只来源于 `eb_system_menu.perms`**；无通配符求值器。
超管拿到的是字面量 `["*:*:*"]`，同样走**精确匹配**，因此**超管也不能访问权限点缺失的接口**（这是第 3.1 节问题的根源）。

### 4.4 【设计缺陷】`GET /api/front/logout` 会写库

**实测**：只要发一个 `GET /api/front/logout`（带上有效 token），会员就被置为注销：

```sql
SELECT uid, phone, is_logoff, logoff_time FROM eb_user WHERE uid=55;
-- 55 | 13800138000 | 1 | 2026-10-28 15:13:16
```

影响：
1. **登出用了 GET** —— 会被浏览器预取、被爬虫、被任何 `<img src>` 触发，属 CSRF 类设计缺陷。
2. 注销后该手机号**无法再登录**（登录查询带 `is_logoff=false` 条件，见 `LoginServiceImpl:68` → `userService.getByPhone`，SQL 为 `WHERE (phone = ? AND is_logoff = ?)`），实测报 `{"code":500,"message":"此账号未注册"}`。
3. 本次审计中我的只读探测脚本正是因此把演示账号顶下线（已复位 `is_logoff=0`）。
4. **建议**：改为 `POST`，并加 CSRF token；或至少不要把 `is_logoff` 写进登出流程。

### 4.5 【设计缺陷】后台接口把除零/空集合异常暴露为原始异常信息

`IndexOutOfBoundsException`、`NumberFormatException: For input string: "id"` 等未经包装直接返回，会向客户端泄露内部实现细节。建议在 `GlobalExceptionHandler` 增加兜底包装。

### 7.3 砍掉的具体操作方式

**推荐做法（可逆、零风险）：隐藏菜单，而不是禁用接口**

```sql
-- 方式一：隐藏一级菜单及其所有子菜单（推荐）
-- 以「营销」为例，一级菜单 id=7；先查子菜单
SELECT id,name FROM eb_system_menu WHERE pid=7 OR pid IN (SELECT id FROM eb_system_menu WHERE pid=7);
-- 再统一置为不显示
UPDATE eb_system_menu SET is_show=0
 WHERE id=7 OR pid=7 OR pid IN (SELECT id FROM (SELECT id FROM eb_system_menu WHERE pid=7) t);
```

- ✅ 优点：**可逆**（改回 `is_show=1` 即恢复）、不影响权限数据、不影响接口。
- 登录后菜单由 `getMenus()` 返回，**隐藏即不可见**。
- ⚠️ 注意：`is_show` 只控制**菜单可见性**，接口仍可被直接调用。若担心越权，需**同时从角色权限中移除**对应 `perms`。

| 方式 | 适用场景 | 风险 |
|------|---------|------|
| **隐藏菜单**（`is_show=0`） | 首选；产品层面"不做了" | 接口仍可直调 |
| **从角色移除权限**（`eb_system_role_menu` 删行） | 需要真正阻断后台操作 | 需同时清理角色，别误删超管 |
| **禁用接口**（Nginx 层拦截 `/dev-api/api/admin/store/seckill` 等） | 需要硬阻断 | 改 Nginx 需 reload，且有回归风险 |

**不推荐**直接删 `eb_system_menu` 行：会导致菜单树 id 悬空、角色权限对不上，且不可逆。

> **关于第 3.1 节的 44 个 403 接口**：这些不是"砍"的问题，而是**要么修、要么明确放弃**。
> - 想用：把缺失的 74 个权限点补进 `eb_system_menu`（**属改数据，需产品确认**），或把页面布局的 13 行 `is_delte` 改回 0。
> - 不想用：按上面方式隐藏对应菜单即可，**无需修权限**。

### A.3 生成接口清单（脚本内嵌，可直接复跑）

以下是本次枚举所用的 PowerShell 脚本（已内含**剥离注释**逻辑，这是避免误报 404 的关键）。保存为 `enum.ps1` 后运行：

```powershell
$root = "D:\project\StorApp\crmeb_java\crmeb"
$out  = "$root\..\docs\接口清单.tsv"
$rows = New-Object System.Collections.Generic.List[string]
$apps = @(@{n="admin";d="$root\crmeb-admin"}, @{n="front";d="$root\crmeb-front"})

foreach ($app in $apps) {
  foreach ($f in (Get-ChildItem $app.d -Recurse -Filter "*Controller.java")) {
    $raw = [System.IO.File]::ReadAllText($f.FullName)
    # ★ 必须剥离注释，否则会把注释掉的接口算进来（本次就因此误报过 templatedianzi）
    $txt = [regex]::Replace($raw, '(?s)/\*.*?\*/', '')
    $txt = [regex]::Replace($txt, '(?m)//.*$', '')
    $base = ""
    $m = [regex]::Match($txt, '@RequestMapping\(\s*(?:value\s*=\s*)?"([^"]+)"')
    if ($m.Success) { $base = $m.Groups[1].Value.Trim('/') }
    $tag = ""
    $t = [regex]::Match($txt, '@Api\(\s*tags\s*=\s*"([^"]+)"')
    if ($t.Success) { $tag = $t.Groups[1].Value }
    $pat = '(?s)@RequestMapping\((?<a>[^)]*)\)|@(?<v>Get|Post|Put|Delete|Patch)Mapping\((?<b>[^)]*)\)'
    foreach ($mm in [regex]::Matches($txt, $pat)) {
      $short = $mm.Groups['v'].Success -and $mm.Groups['v'].Value -ne ""
      if ($short) { $verb = $mm.Groups['v'].Value.ToUpper(); $args = $mm.Groups['b'].Value }
      else        { $verb = ""; $args = $mm.Groups['a'].Value }
      $path = ""
      $p = [regex]::Match($args, '(?:value\s*=\s*)?"([^"]*)"')
      if ($p.Success) { $path = $p.Groups[1].Value }
      if ($verb -eq "") {
        $rm = [regex]::Match($args, 'RequestMethod\.([A-Z]+)')
        if (-not $rm.Success) { continue }     # 类级 @RequestMapping，无 method
        $verb = $rm.Groups[1].Value
      }
      if ($path -eq "" -or $path -eq "/") { continue }
      $full = ("/" + $base.Trim('/')).TrimEnd('/') + "/" + $path.TrimStart('/')
      $rows.Add(($app.n + "`t" + $f.Name + "`t" + $tag + "`t" + $verb + "`t" + ($full -replace '//+','/')))
    }
  }
}
[System.IO.File]::WriteAllLines($out, $rows, (New-Object System.Text.UTF8Encoding($true)))
"TOTAL=$($rows.Count)"
```

> 对照线上版本：把 `$root` 换成 `/opt/storapp/crmeb` 并改用 bash/perl 等价实现，产出两份 `app|verb|path` 后做集合 diff，即可复现"0 处错配"的结论。
