## 2026-10-12 会话（二）：图片输入排查 + 编码备忘

### 问题：会话不能传图片，提示"模型不支持"

**根因**：该会话的模型选择是 `deepseek-v4-flash`，它是**纯文本模型**。

**实测结论**（api.scnet.cn 网关 + 215KB 真实截图，看 prompt_tokens 是否包含图片）：

| 模型 | prompt_tokens | 结果 |
|------|--------------|------|
| `deepseek-v4.1-flash` | 238 | ✅ 准确读出图内文字（红色 FAIL: / bucket-820->snap-63） |
| `deepseek-v4-flash` | 94 | ❌ 回"没看到图片" |
| `deepseek-v4-pro` | 15 | ❌ 回"看不到图片" |
| `glm-5.3` | — | ❌ 回"没有多模态输入能力" |

**结论**：网关侧**只有 `deepseek-v4.1-flash` 支持图片**；其余模型即使传 `image_url` 也会被丢弃。

**已做**：
- 模型名加防呆标注：`DeepSeek-V4.1-Flash 🖼 支持图片` / 其余标 `（纯文本）`
- `agent-default-model` 确认为 `deepseek-v4.1-flash`（新会话默认可传图）
- settings.yaml 顶部加**视觉模型备忘** + **编码模式备忘**

### 编码模式备忘（重要）

规则按**文件类型**区分：

| 文件 | 编码 | 原因 |
|------|------|------|
| `settings.yaml` / `package.json` / `*.yml` | **UTF-8 无 BOM** | 有 BOM 会导致解析失败、服务起不来 |
| `*.ps1` 脚本 | **UTF-8 with BOM** | PowerShell 5.1 才能正确显示中文 |

禁止用 PowerShell `Set-Content -Encoding UTF8` 写配置（会带 BOM），改用 `write` 工具或
`[System.IO.File]::WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($false))`。

> 教训：2026-10-12 曾把 `profiles/web/package.json` 存成 UTF-8 with BOM，
> 导致 dsh web 解析 JSON 失败、重启起不来。

### 其他

- `todo-widget` 安装方式由 `file:`（副本）改为 `link:`（junction），改源码后**只需重启**、不必手动复制。
  > 注：切换时 pnpm 会因 `cloudflared` 目录被隧道进程占用而失败，可手动 `mklink /J` + 改 package.json 协议解决。

## 2026-10-13 会话：桌面版（DSH Desktop）配置适配

### 问题：家里桌面版崩溃，报 403 client 相关

**根因**：`setup.ps1` 把 **Web 版 settings.yaml 覆盖到共享位置** `~/.dsh/settings.yaml`，
其中的 **`remote-web-ui`** 配置（随 `@linxin666/dsh-web-all` 安装）在桌面版上闯祸：

1. `lanBind: true` → webserver 绑 `0.0.0.0`
2. `requirePairingForLan` 默认 true → 启用**配对门控**
3. 桌面版 Electron 渲染进程访问 `/api` 被判为未配对来源 → **HTTP 403**

### 关键事实：桌面版 vs Web 版

| 项目 | Web 版 | 桌面版 |
|------|--------|--------|
| profile 目录 | `~/.dsh/profiles/web/` | `~/.dsh/profiles/desktop/`（Electron 独占） |
| 插件安装 | `dsh plugin --profile web add <pkg>` | 应用内插件管理（CLI 禁止操作 desktop） |
| `settings.yaml` | **共享** `~/.dsh/settings.yaml` | **同一份** ⚠️ |

> Electron 侧约束（`apps/desktop/src/project-manager.ts`）：
> `DESKTOP_PROFILE_BUNDLES = ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app']`，
> 且 `dsh` CLI 有 `rejectElectronProfile` 拒绝操作 desktop profile。

### 已做修复

1. **新增 `.dsh/settings.desktop.yaml`** —— 桌面版精简模板，剔除 `remote-web-ui`、
   `skin-*`、`pet`、`dsh-usage` 等 Web 专有配置，只保留模型路由/默认模型/预设。
2. **重写 `setup.ps1`** —— 加 `-Mode auto|web|desktop`：
   - `auto`（默认）：检测到 `~/.dsh/profiles/desktop` 就按桌面版处理
   - `desktop`：用精简 settings + **不复制 `profiles/`** + 检查 desktop profile 是否误装 web-all
   - 覆盖 settings 前自动备份
3. **README** 增加「桌面版特别注意」章节，说明 403 成因与避免方式。

### 家里修复步骤

```powershell
cd dsh_workspace

.\setup.ps1 -Mode desktop      # 覆盖掉含 remote-web-ui 的 settings
# 若桌面版应用内装过 @linxin666/dsh-web-all → 在应用内插件管理里卸载
```

## 2026-11-05 会话：BlueField-3 DPU 卡排障（DPU 模式 → NIC 模式）

> **完整的排查过程、可复用命令、回滚方式和硬件清单见
> [`BlueField-3-DPU转NIC模式排查.md`](BlueField-3-DPU转NIC模式排查.md)**

### 问题

服务器 `node20-39`（`10.17.21.85`，登录密码见密码管理器）上的一张 BlueField-3 卡：
`mst status` 能看到它，但 `ip a` 完全没有网卡、`ibstat` 里也没有对应的 IB 设备。
`lspci` 三个 function 都在，`mlx5_core` 一个都没绑上。

### 根因

卡被配成 **DPU 模式**（`INTERNAL_CPU_MODEL=EMBEDDED_CPU(1)`），而 DPU 的 **ARM 侧没有任何可启动系统**
（`BOOT_MODE=1 (emmc)`，但 eMMC 里没有 BFB；`console` 采样 30 秒零输出、`bfdump` Timeout、`OPN_STR=N/A`）。

DPU 模式下 host PF 的固件初始化**依赖 ARM 供给资源**：

```
INTERNAL_CPU_PAGE_SUPPLIER    ECPF(0)   ← host PF 的固件内存页由 ARM 供给
INTERNAL_CPU_IB_VPORT0        ECPF(0)   ← IB vport0 归 ARM
```

ARM 不干活 → 页供给不上 → 固件永远停在 `pre-initializing (0x87010000)` →
驱动等 120 秒后 `-110 (-ETIMEDOUT)` 超时 → probe 失败 → 不出网卡。

`mst` 之所以还能看到卡，是因为它走 **PCI 配置空间裸访问**，不需要驱动。
**所以「`mst` 有卡但 `ip a` 没网卡」这个组合，第一嫌疑就是固件初始化失败，直接看 dmesg。**

### 修复

```bash
mlxconfig -d /dev/mst/mt41692_pciconf0 -y set INTERNAL_CPU_MODEL=SEPARATED_HOST
# 然后【必须断 AC 冷启动】才能生效
```

**⭐ 最大的教训：`INTERNAL_CPU_MODEL` 无法用任何软件复位生效。** 逐条试过全部失败：

| 尝试 | 结果 |
|---|---|
| `mlxfwreset -l 4 -t 0`（全芯片热重启） | ❌ `fsm sync timed out` |
| `mlxfwreset --sync 1` | ❌ 被工具忽略（`reset sync argument is ignored when reset level is not PCI_RESET`） |
| `mlxfwreset reset_fsm_register` 清 FSM | ⚠️ FSM 清成功，重试**仍** timeout |
| rshim `SW_RESET 1`（SoC 软复位） | ⚠️ **确实重启了 SoC**（`UP_TIME` 21941s → **42s**），但 `BF_MODE` 仍是 `DPU mode` |
| PCIe 槽位电源 `/sys/bus/pci/slots/3/power` | ❌ 未暴露 |
| PCI PM D3hot→D0 | ❌ 设备 `NoSoftRst+`，不触发内部复位 |

`fsm sync timed out` 的成因：复位 FSM 打印 `Waiting for mlxfwreset to run on all other hosts`，
它要等 ARM host 应答，而 ARM 没系统**永远不应答** —— 这个死锁本身就是"卡在 DPU 模式"的后果。

**断电方式也得注意**：`reboot` 不够（槽供电不断）；`poweroff` + 按电源键**也不一定够**
（S5 下槽位常保留辅助供电，且该卡自带 integrated BMC）。**只有断 AC 是确定有效的。**

### 结果

- `mlx5_core` 绑定成功，`enp59s0f0np0` / `enp59s0f1np1` 出现，`ibstat` 的 CA 数 **4 → 6**
- **端口 2 `enp59s0f1np1`：UP，`100000Mb/s` 全双工，`carrier=1`，`Link detected: yes`** ✅
- 端口 1 `enp59s0f0np0`：`NO-CARRIER` —— 该笼子**物理上没插模块**
  （`mlxlink` 报 `Cable is unplugged`、`ethtool` 报 `Link detected: no (No cable)`）
- 新增 `/etc/systemd/network/20-bf3-nic.network`：**只保链路 up，不配 IP、不发 DHCP**
  （`enp59` 未收录进 `/etc/netplan/00-installer-config.yaml`，所以开机后原本是 admin down）

### `openibd.service` 的 failed 是症状（2026-11-10 更正）

先前记为「inbox → OFED 驱动切换残留」，**不准确**。`openibd` 有 **180 秒**启动超时，
而 BF3 故障时两个 PF 各卡满 **120 秒**的 pre-init 等待（2×120s > 180s）
→ openibd 等不到设备，**超时失败**。

三次观测一致：BF3 坏 → `failed`（11-05）／BF3 好 → `active`／BF3 又坏 → `failed`（11-10）。
**以后再看到它 failed，先查 Mellanox 卡的 dmesg 有没有 probe 失败**；
`systemctl restart openibd` 能"修好"只是因为那时 probe 早已失败完、脚本没有设备可等 —— 治标不治本。

### 本次新增的环境认知（已写进独立文档）

- **`rshim` 不需要内核模块** —— 该包只有用户态，其 PCIe 后端通过 `resource0` 直映射 BAR
  访问 `3b:00.2`。`PCIE_HAS_VFIO=1 rshim -b pcie` 即可读 `/dev/rshim0/misc`。
  （DOCA 仓里也没有 `rshim-dkms`，`/usr/src` 里没有源码——但都不需要。）
- ⚠️ **`BF_MODE` 在本卡上不可信（此条先前写错，2026-11-10 已更正）** —— 它读的是 rshim 的
  `SCRATCHPAD2` 暂存寄存器，由 **DPU 侧（ARM/ATF）写入上报**，主机侧 `mlxconfig` 不碰它。
  本卡 ARM 从未启动 → 没人更新它 → 一直显示 `DPU mode`（两种模式下都一样）。
  **判断模式只认 ⭐ `mlxconfig -d <dev> q INTERNAL_CPU_OFFLOAD_ENGINE`**
  （`ENABLED(0)`=DPU / `DISABLED(1)`=NIC / `RO` 前缀=Zero Trust）。详见独立文档 6.7 节。
- **`INTERNAL_CPU_RSHIM` 不要关** —— 与 PF 探测无关，且它正是排障通道。
- ⚠️ 排查用到的 SSH 密码**不入库**（见上方安全提示），文档中一律用占位符。
- 服务器**无外网**（`github.com` 解析失败，apt 仅 sugon 镜像 + 本地 DOCA 仓），
  需要 BFB / 固件包时得从外部传入。

```bash
#   DISABLED(1) = NIC 模式
#   带 RO 前缀  = DPU 模式 + Zero Trust（只读）
```

### ⭐ 突破一：`mlxconfig -e q` 的三列语义（先前判反过一次）

准确列名是 **`Default | Current | Next Boot`**：

```
Configurations:                        Default          Current           Next Boot
        INTERNAL_CPU_MODEL             EMBEDDED_CPU(1)  EMBEDDED_CPU(1)   EMBEDDED_CPU(1)
   *    INTERNAL_CPU_PAGE_SUPPLIER      ECPF(0)          EXT_HOST_PF(1)    EXT_HOST_PF(1)
   *    INTERNAL_CPU_ESWITCH_MANAGER    ECPF(0)          EXT_HOST_PF(1)    EXT_HOST_PF(1)
   *    INTERNAL_CPU_IB_VPORT0          ECPF(0)          EXT_HOST_PF(1)    EXT_HOST_PF(1)
   *    INTERNAL_CPU_OFFLOAD_ENGINE     ENABLED(0)       DISABLED(1)       DISABLED(1)
```

- 行首 `*` = **与出厂值不同**；`Default` 列 = **DPU 模式** ⇒ **该卡出厂就是 DPU 模式**
- ⭐ **`Current` 列 = NIC 模式** ⇒ **配置确实已经生效**
- ⚠️ 普通 `mlxconfig q` 只有 `Next Boot` **一列，不能用来判断是否已生效**

### ⭐⭐ 突破二：`BF_MODE` 其实是可信的（推翻我 11-10 下午的结论）

| 数据点 | `INTERNAL_CPU_MODEL` | `INTERNAL_CPU_OFFLOAD_ENGINE` | `BF_MODE` |
|---|---|---|---|
| ① 11-05 切 NIC 后 | `SEPARATED_HOST(0)` | `ENABLED(0)`（**从未被改过**） | `DPU mode` |
| ② 11-10 还原后 | `EMBEDDED_CPU(1)` | `ENABLED(0)` | `DPU mode` |
| ③ **11-10 走官方路径** | `EMBEDDED_CPU(1)` | **`DISABLED(1)`** | **`NIC mode`** ✅ |

⭐ **`BF_MODE` 与 `OFFLOAD_ENGINE` 100% 一致。** ① 之所以显示 `DPU mode`，
是因为当时 `OFFLOAD_ENGINE` **根本没被改过**（仍是出厂 `ENABLED(0)`）—— **它报得没错**；
是我拿它去跟 `INTERNAL_CPU_MODEL` 比，才得出"不可信"的错误结论。

→ **`BF_MODE` 跟随 `INTERNAL_CPU_OFFLOAD_ENGINE`，不跟随 `INTERNAL_CPU_MODEL`。**
（但它的边界是：只反映"ATF 认为该用哪个模式"，**不代表 PF 真能起来**。）

### 🔴 最终结论：三个层面全是 NIC 模式，PF 依然起不来

```
flash (Next Boot)    = NIC 模式  ✅
运行中 (Current)     = NIC 模式  ✅
卡侧寄存器 (BF_MODE) = NIC 模式  ✅
mlxfwreset q         = Reset-reason: Cold reset   ← 证明真的冷复位过
host PF              = pre-initializing 超时 -110  ❌
```

**配置这条路已经走到头了。** 机制：官方路径下 `INTERNAL_CPU_MODEL` 仍是 `EMBEDDED_CPU`

11-05 用弃用的 `SEPARATED_HOST` 能成，是因为它把这条路**整个删掉、绕过了交接**
（代价：`OFFLOAD_ENGINE` 一起消失）。

### 3. ⭐ 新知识一：`DISPLAY_LEVEL` 决定 `misc` 里有没有引导日志

`/dev/rshim0/misc` 的 `Log Messages` 段**只有 `DISPLAY_LEVEL=2` 才有内容**。


### 4. ⭐ 新知识二：`SW_RESET` 能救"推流撞车"僵死的卡

对照机 15:36 发生了一次"**网卡全部消失**"，`dmesg -T` 现场：

```
[Tue Nov 10 15:36:07] mlx5_core 0000:99:00.1: SW reset semaphore is already in use   ← 关键
[Tue Nov 10 15:36:07] mlx5_core 0000:99:00.1: handling bad device here
[Tue Nov 10 15:36:07] mlx5_core 0000:99:00.1: mlx5_handle_bad_state: starting teardown
[Tue Nov 10 15:36:08] rshim[2738]: rshim0 boot open      ← 有人推引导流（写 /dev/rshim0/boot）
[Tue Nov 10 15:36:11] rshim[2738]: rshim0 boot close     ← 3 秒就断 = 推流失败
```

**机制**：rshim 推流要复位设备，`mlx5_core` 也在复位路径上，**两者抢同一个 SW reset 信号量**
⇒ 卡被拖进"坏设备"流程 teardown ⇒ **netdev 全没**。

**解药**（实测约 100 秒恢复）：

```bash
echo "SW_RESET 1" > /dev/rshim0/misc
```

| 故障 | `SW_RESET` 有用吗 |
|---|---|
| 推流撞车 ⇒ 驱动 teardown、netdev 消失 | ✅ **有用**（16:12 下发，16:13:54/57 `health recovery succeeded`） |
| ATX 未接 ⇒ BL31 halt | ❌ **没用**（老机器试过） |

⇒ 排查文档里"`SW_RESET` 没用"的说法已**收窄**为"救不了缺线，但能救撞车"。
**判断顺序：先看 BL31 有没有 ATX 报错，再看是不是撞车。**
