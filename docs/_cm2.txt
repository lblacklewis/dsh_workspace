feat: 处方药下单精确匹配（处方必须开着这个药）

背景
此前只校验「有没有有效处方」，不校验处方里是否恰好包含所购药品。
结果是一张治感冒的处方也能买降压药 —— 合规上说不过去。

设计上的关键判断
不能一刀切做精确匹配，因为处方有两个来源：
  a) 合作互联网医院回传 —— eb_prescription_product 有用药明细，可精确匹配
  b) 用户手工上传处方照片 —— 没有明细，根本无法匹配
对 b) 类处方只能退回「有有效处方即放行」。缺数据是系统能力的欠缺，
不该由用户承担后果 —— 一刀切会把大量正常用户拦死。

实现
checkRxProductsCovered() 改为：
  - 取出该用户所有「已审核通过 + 未过期」的处方及其明细
  - 商品在明细里 -> 放行
  - 商品不在明细里，但该用户还有一张「没有明细的有效处方」-> 放行（回退）
  - 否则 -> 拦截
一张处方可对应多个商品（一方多药，慢病常见）。

踩过的坑
我按自己设想的结构写了 CREATE TABLE IF NOT EXISTS eb_prescription_product，
表其实在更早的处方模块里就建好了（结构是 id/prescription_id/product_id/
sku_id/quantity/create_time，比我设计的还完整），所以建表被静默跳过，
但实体里多了个 drug_name 字段，运行时报 Unknown column 'drug_name'，
又被全局异常处理包成「服务器数据异常，请联系管理员」，完全看不出是列名问题。
教训：让实体适配已有表，不要让表适配实体；CREATE TABLE IF NOT EXISTS
在结构不符时会静默通过，是个隐蔽陷阱。

实测（每步都清了历史数据，避免上一轮的处方干扰判定）
  [A] 有效处方无明细（手拍上传）         -> PASSED
  [B] 唯一有效处方有明细、开的是别的药   -> BLOCKED
  [C] 唯一有效处方明细里就是该商品       -> PASSED
日志印证：处方覆盖校验通过：有效处方 N 张，明细 M 条

未做（明确留待处理）
拦截时的提示语目前是「请先上传处方并经药师审核通过」，但在 [B] 场景下
用户其实已经有审核通过的处方，只是没开这个药 —— 文案有误导性。
应区分「没有处方」和「处方未覆盖该药品」两种情况，下一轮修。
